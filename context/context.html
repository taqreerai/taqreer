AI Presentation Platform

Taqreer Full-Stack Web App Architecture

A complete product and technical plan for Taqreer (taqreer.ai): an Arabic-first, RTL AI presentation platform where users provide content, Claude designs the deck, and users review, comment, regenerate, or export. There is no manual slide editor — Claude does all the design work.

Product Type AI presentation generator (Arabic-first, RTL)
Stack Next.js 16, TypeScript, Tailwind, Prisma/Postgres, Inngest, Supabase, Anthropic Claude API
Core Output PPTX, PDF, saved projects, reusable templates
Main Differentiator Promptless brand-aware generation; no manual editing — every change goes through Claude

01. Product Overview

Taqreer turns content into beautiful Arabic presentations. The user provides content, brand assets, an existing deck to improve, a reference deck to mimic, or a template to start from. Claude generates the slide design as structured JSON. The user lands in the Preview Window to review, comment on specific areas (Claude redesigns them), regenerate the whole deck, export to PPTX/PDF, or save as a template.

Flow 1 — Create (إنشاء)

Start from scratch. User pastes/uploads content, sets brand (palette, fonts, logo), and Claude designs a fresh deck.

Flow 2 — Enhance (تحسين)

Upload an ugly PPT. Claude extracts its existing theme/palette/fonts and redesigns the layout while preserving the original visual identity.

Flow 3 — Mimic (محاكاة)

Upload your content + a reference deck whose style you admire. Claude extracts the reference's style contract and rebuilds your content in that style. Iterative review loop.

Flow 4 — From Template (إنشاء من قالب)

Pick a template from the library, add content, and Claude maps the content into the template's design system. No brand wizard — the template supplies the design tokens.

Core product rule: every journey ends inside the Preview Window. The preview is review-only — users browse slides, comment on areas (which fires area.redesign.requested to Claude), regenerate the whole deck, export to PPTX or PDF, or save as a template. There is no manual slide editor — Claude does all the design work.

02. Product Flows

Four primary flows on the dashboard, RTL right→left: Create, Enhance, Mimic, From Template.

Flow 1: Create (إنشاء) — start from scratch

Dashboard tile 1 → /create/content. Three-step wizard, brand decided fresh by Claude.

1
Content (/create/content)Upload PPTX/PDF/DOCX/TXT/images or paste text.
2
Brand & Settings (/create/brand)Upload a palette screenshot for Claude vision or pick colors manually; upload heading + body fonts and logo; pick slide size and count.
3
Editable Summary & Rules (/create/summary)Two cards: brand (palette, fonts, logo, generation rules — tone, design style, fix typos, pagination, persistent overlay) and content (editable textarea + Edit/Save). CTAs: إنشاء or إنشاء وحفظ كهوية بصرية. POST /api/projects → redirect straight to /preview/[projectId].
4
Generate (/preview/[projectId])Fires Inngest deck.generate.requested. The preview page itself handles the generating state — placeholders with per-card progress (done ✓ / current / pending), polled from /api/projects/[id]/status. When complete, slides cascade in and the vertical toolbar slides in from the left.

Flow 2: Enhance (تحسين) — preserve original theme/colors

Dashboard tile 2 → /enhance. Goal: make an ugly PPT better while keeping its original visual identity. Claude redesigns layout/typography/hierarchy but does not invent a new theme.

1
Upload (/enhance)PPTX-only upload. Advanced options: keep colors, keep fonts, custom instructions.
2
Review (/enhance/review)Claude extracts and shows the original palette, fonts, logo, and slide structure, plus a plain-Arabic redesign plan. The user can override any extracted asset before confirming.
3
GenerateFires deck.generate.requested with type: "enhance" and the extracted (possibly overridden) brand contract. Lands on shared preview.

Flow 3: Mimic (محاكاة) — redesign in a reference style

Dashboard tile 3 → /mimic. Take your content and rebuild it in the style of a reference deck you admire. Two uploads, iterative review.

1
Your content (/mimic/content)Upload PPTX/PDF/DOCX/TXT or paste the content to redesign.
2
Reference style (/mimic/reference)Upload a PPTX whose visual style you want to match. Claude extracts the reference style contract: palette, fonts, layout idioms, accents.
3
Review — iterative (/mimic/review)Claude shows the extracted reference style and a slide-by-slide design plan. User confirms, or adds a prompt → Claude refines → updated review → loop until confirmed.
4
GenerateFires deck.generate.requested with type: "mimic" plus content + reference style contract. Lands on shared preview.

Flow 4: From Template (إنشاء من قالب) — pick template, add content

Dashboard tile 4 → /templates. Replaces the earlier "Create Template From Scratch" concept entirely — there is no separate custom-design flow; the design comes from a pre-existing template, and the user just contributes content.

1
Browse library (/templates)Grid of templates with search and filters (category, industry, language, direction, plan). Each card has a إنشاء من هذا القالب CTA.
2
Add content (/templates/[id]/content)Upload PPTX/PDF/DOCX/TXT or paste. Slide-count options. No brand wizard — the template supplies the design system.
3
GenerateFires deck.generate.requested with type: "custom" and the template's style_contract applied as the design system. Lands on shared preview.

08. AI Pipeline

The AI system should be split into multiple controlled stages instead of one large prompt. Each stage should return structured data and pass validation before moving to the next stage.

2
Analyze brandExtract colors, typography, logo rules, image style, tone, and layout patterns.
3
Generate outlineCreate presentation title, sections, slide list, and slide objectives.
4
Create slide narrativeDefine the role of each slide and the message it should communicate.
5
Select layoutsMap each slide to a suitable slide type.
6
Generate slide JSONCreate structured slide elements, positions, styles, and assets.
7
Validate outputCheck schema, overflow, missing assets, coordinates, and RTL rules.
8

1. Upload original PPTX
2. Parse slides into internal JSON
3. Extract current palette, fonts, logo, slide structure (Claude vision)
4. Show extraction + redesign plan on /enhance/review for user confirmation/override

6. Zod validate; self-healing retry on failure
7. Save to PresentationVersion

3. Extract content from your upload
4. Extract style contract (palette, fonts, layout idioms) from reference (Claude vision)

7. Zod validate; self-healing retry on failure

09. Preview Window

The Preview Window is review-only — there is no manual slide editor. Users do not drag, resize, or type on a slide. Claude does all the design work; the user's interaction after generation is to review, comment, regenerate, export, or save as a template.

Layout

┌────────────────────────────────────────────────────────────┐
│  Action bar:  أعد التصميم  ·  تصدير PPTX  ·  تصدير PDF  ·  حفظ كقالب  │
├──────────────────────────────────┬─────────────────────────┤
│                                  │  Slide 1                │
│      Main slide view             │  Slide 2                │
│      (1920×1080 rendered as      │  Slide 3  ← selected    │
│       HTML/CSS, scaled to fit)   │  ...                    │
│                                  │  Slide N                │
└──────────────────────────────────┴─────────────────────────┘

What the user can do

  • Browse slides via the right-side slide panel
  • Click-and-drag to select an area on the main slide → opens a comment box → submits to area.redesign.requested Inngest job → Claude updates JSON for those elements → slide re-renders
  • Trigger a full regeneration with the same brief (action bar أعد التصميم)
  • Export as PPTX (PptxGenJS, via deck.export.requested)
  • Export as PDF (Puppeteer, via deck.export.requested)
  • Save the deck as a template (style contract + thumbnails + PPTX artifact, via template.save.requested)

What the user cannot do

Move elements. Resize elements. Change font/color manually. Add a text box. Reorder slides by hand. Undo to a previous "manual edit." None of these exist. Every visual change goes through Claude via a comment or a regen — that's the deliberate product constraint that keeps the JSON-first architecture coherent.

Rendering approach

Slides render as HTML/React using absolute-positioned elements on a fixed 1920 × 1080 canvas. The same coordinate system is used for the preview itself, slide-panel thumbnails (via html2canvas when saving as a template), PPTX export (PptxGenJS), and PDF export (Puppeteer printing the HTML). The renderer component lives at components/slides/SlideRenderer.tsx.

Current implementation status

As of 2026-05-12, /preview/[projectId] lives inside the (app) route group and is the unified surface for generating / completed / failed states. The vertical Photoshop-style action bar (Regenerate · Export PPTX · Save as Template) is built, slides cascade in opacity-only with Framer stagger, and per-card progress (done ✓ / current spinner / pending pulse) is fed by polling /api/projects/[id]/status at 1.5 s. The slide-panel side navigation, area-select-and-comment overlay, and per-element shadow/border rendering are still not built — see §15 Implementation Status.

12. Export System

The export service converts internal presentation JSON into external formats. Export jobs should run in the background.

Read presentation JSONUse the saved deck as the source of truth.
2
Convert slide dimensionsMap 1920 × 1080 coordinates to 16:9 PowerPoint size.

4
Generate PPTXCreate the file and store it in object storage.

PDF Export Options

Option A: HTML to PDF

Render slides in the browser using the same React slide renderer, then export to PDF with Playwright or Puppeteer. Best for MVP fidelity.

Option B: PPTX to PDF

Generate PPTX first, then convert to PDF using a worker with LibreOffice. Better for PowerPoint consistency, but more infrastructure-heavy.

MVP recommendation: start with PPTX export and HTML-to-PDF export. Add LibreOffice conversion later if needed.

Lessons learned — do not repeat

PowerShell shadows ANTHROPIC_API_KEY

The PowerShell harness used in this project exports ANTHROPIC_API_KEY="" as an empty string. Next.js gives shell-env precedence over .env.local, so process.env.ANTHROPIC_API_KEY ends up empty despite a valid key in the file.

Fix: always Remove-Item env:ANTHROPIC_API_KEY -ErrorAction SilentlyContinue before npm run dev. Confirm with: Get-ChildItem env:ANTHROPIC* — if the var is listed with a blank value, this is the issue.

Anthropic SDK client must be lazy

new Anthropic() at module load captures whatever process.env.ANTHROPIC_API_KEY is at import time. If env loading races module load, the client captures empty permanently.

Fix: wrap construction in a getClient() function called inside step.run() at request time, and throw a clean error if the key is still missing.

Slide schema too complex for structured outputs

Passing zodOutputFormat(SlideManifestSchema) to output_config.format returns 400 "The compiled grammar is too large". The schema's discriminated unions × deep nesting × many enums blow the strict-grammar limit.

Fix: drop output_config.format; use a strong system-prompt that describes the JSON shape, parse the response text with markdown-fence stripping, validate with Zod, and retry with the validation error appended to the prompt (3 attempts inside the Inngest step). This is the "self-healing" pattern from the brief.

Strip previewDataUrl from Claude input

The Create wizard sent the logo as a base64 data URL (previewDataUrl) in addition to the storage URL. That bloated each Claude call by ~3000 input tokens for no benefit — the renderer can use storageUrl alone.

Fix: drop previewDataUrl when building the Claude-bound brief in app/api/projects/route.ts (already applied 2026-05-11).

Prisma table names are PascalCase

When querying directly from psql, table names must be double-quoted PascalCase: "PresentationVersion", "Presentation", "Project", etc. — not snake_case. Same for column names: "slideJson", "presentationId", "createdAt".

Inngest function updates v1 (don't create v2)

POST /api/projects creates a v1 PresentationVersion with status queued. The original deck-generate handler created a new v2 with status completed, leaving v1 stuck at queued forever. The rewrite updates the v1 row using versionId from the event payload. (The new /regenerate route is the correct place to create v_n+1 and fire generation against it.)

PPTX coordinates: px × (SLIDE_W_IN / CANVAS_W) × 72

The CSS-px→pt ratio at 96 DPI is 0.75, but our 1920px canvas is scaled to a 10″ slide — the right factor for font size and positioning is (10/1920) × 72 = 0.375. Using 0.75 doubled every glyph and made stat numbers wrap inside their cards. Also: pick LAYOUT_16x9 (10×5.625″) so the inch-constants match what PptxGenJS expects.

Pick the slide font by script, not role

The earlier rule ("headlines use heading font, body uses body font") tagged Arabic caption/label elements with Poppins (the body font). On any machine without Cairo installed, PowerPoint fell back to a Latin font and the Arabic letters visibly disconnected. The new rule: pick by script. Arabic content → Cairo, Latin → Poppins. Role drives weight/size only.

Send-after-commit is not atomic

Routes that fire Inngest events after a Prisma transaction (/api/projects, /retry, /regenerate, /export, /save-as-template) can leak orphaned "queued" rows if the send fails. Always wrap with sendInngestEventWithRetry (in lib/inngest-helpers.ts) and on final failure revert Project/Version/Job statuses to failed so the UI surfaces a clear error instead of an infinite spinner.

Gradients are back — but as PNG rasters on shapes only

The earlier ban (2026-05-11) was because PptxGenJS can't emit multi-stop linear gradients via its high-level API. The fix in deck-export.ts (2026-05-12): when a shape has fill.type === "gradient", build an SVG with the linear gradient over the shape silhouette (<ellipse>, <polygon>, <rect>) and pipe it through sharp to get a transparent-background PNG at 2× the bbox; then addImage with a base64 data URL. The system prompt now allows gradients on shape fills (un-banned) but still forbids them on slide.background (a full-canvas gradient inflates the file with a big raster).

Multi-run text > BiDi control characters

Trying to anchor mixed-script runs by inserting LRE/PDF (U+202A/202C) and later LRM/RLM (U+200E/200F) into the content string failed: Arial in particular renders the embedding controls as visible boxes, and the marks behave inconsistently across PowerPoint's BiDi engine. The replacement: segmentRuns(content) walks the string and splits at every Arabic↔non-Arabic transition (whitespace clings to the current run); when there's more than one run, addText gets the array form [{text, options: {rtl}}] so each run carries its own direction. Single-script content stays single-string. No invisible chars in the output, neutrals (•·|—) stick to their natural neighbors.

USER RULES override system defaults — at the user-message level

The system prompt is cached (cache_control: ephemeral) — mutating it per-request kills the cache. Instead, the prompt has a top-of-prompt USER RULES (HIGHEST PRIORITY) section that tells Claude rules at the end of the user message win over anything in the system prompt. buildUserMessage emits a "Generation rules" block at the end of every request: tone, design-style (with per-style composition hints like "creative → asymmetric, full-bleed, unusual angles" / "newspaper → multi-column + sidebars"), typo policy, pagination on/off (off explicitly cancels the system prompt's pagination requirement), persistent overlay (text + position + exclusions), verbatim mode (create flow), and logo placement. Cache stays hot; behavior is per-request.

Bbox height must budget for fontSize × lineHeight

Claude was setting fontSize: 220 in a height: 220 bbox. At lineHeight: 1.5 a single line of 220-px text needs ~330 px of vertical space — the text overflowed the bbox and crashed into the next element below (this is the "Taqreer overlapping the Arabic subhead" bug). Fix: explicit TYPOGRAPHY rule in the system prompt ("Box height ≥ fontSize × lineHeight × line count") with worked examples, plus tightened default lineHeights by role (headline 1.1, subheading 1.2, body 1.5, caption 1.4).

Progress in slideJson, polled — Realtime not required

Original plan: stream progress via Supabase Realtime on the presentation_versions table. Reality: Realtime depends on the table being added to the supabase_realtime publication, which wasn't reliable, and the client was actually completing decks via polling all along. Current setup: deck-generate.ts subscribes to stream.on("text"), counts "slideId": occurrences = current slide, throttles DB writes (~800 ms) into slideJson.progress = { stage, currentSlide, estimatedTotal }. /api/projects/[id]/status exposes that progress; DeckView polls every 1.5 s during generation and renders per-card UI (done ✓ / current spinner / pending pulse). Realtime can still fire on top of this — it just isn't load-bearing.

Sync server props into client state on router.refresh()

DeckView holds manifest in useState(initialManifest). The polling fallback that triggers router.refresh() when status flips to "complete" updates the server-rendered props — but useState only seeds on mount, so the client stayed stuck on "generating" forever in an endless refresh loop. Fix: a useEffect that pulls initialManifest into state when it goes null → non-null (generation completed), AND clears the cached manifest when the server reports a queued version (regenerate flow). Two-way prop ↔ state sync covers both transitions.

16. Technical Risks and Recommendations

These are the main areas that can slow development or affect output quality.

PPTX import is complex

Do not promise perfect PPTX-to-slide-JSON conversion at MVP stage. The Enhance flow's PPTX parsing should extract palette, fonts, logo, content outline, and rough slide structure — Claude redesigns from there. Don't aim for pixel-perfect round-tripping.

AI layout quality can vary

Use strict slide types, layout templates, schema validation, overflow checks, and design scoring.

Export fidelity can break

Use the same 1920 × 1080 coordinate system across the Preview Window, thumbnails, PDF, and PPTX export.

RTL cannot be added later

Arabic direction, right alignment, font fallback, and RTL layout rules must be part of the initial schema.

Critical recommendation: avoid letting Claude's output land in PresentationVersion.slideJson without validation. Every Claude response goes through Zod validation; on failure, retry with the validation error appended to the prompt (self-healing pattern). After 3 failed attempts the Inngest job fails and surfaces in Sentry.

18. Pivot — dom-to-pptx (decided 2026-05-13)

After a week of patching BiDi, coordinate math, gradient rasterization, and logo placement on top of PptxGenJS, the JSON-manifest architecture is being replaced by an HTML-first pipeline using dom-to-pptx. Claude will author each slide as HTML/CSS, the browser does layout, and the library measures the rendered DOM to emit a native PPTX. Preview and export become the same artifact — no more divergence.

Why we pivoted

  • BiDi was death-by-a-thousand-cuts. Three rounds of fixes (multi-run text in export, <bdi> in renderer, dir attribute, prompt instructions) and the bullets-on-wrong-side / leading-colon / mixed-script-flip bugs kept resurfacing. Root cause: we were hand-coding a layout system that the browser already does correctly.
  • The schema was a leaky abstraction. Every new visual feature (gradients, shadows, logo contrast band, RTL bullet anchoring) became another rule in the system prompt and another branch in the renderer. Claude was being asked to do designer math (bbox = fontSize × lineHeight × lines, mirror x for RTL, etc.) instead of designing.
  • The renderer and the export kept drifting. What previewed in React didn't match what came out of PPTX — gradients especially. Mixed-script ordering was different between web and PowerPoint.

What dom-to-pptx gets us

Browser does layout

Flexbox, grid, abs-positioning, RTL — already solved problems in the browser. The library reads getBoundingClientRect() + computed styles and maps that to PPTX coordinates. No more positional math in the prompt.

Native gradients + shadows + border-radius

CSS linear-gradient becomes a real OOXML vector gradient. box-shadow becomes a PPT outer shadow. border-radius maps to rounded corners. filter: blur() maps to soft-edge effects. We delete the sharp-based gradient rasterizer.

SVGs stay vector

With svgAsVector: true, SVG icons and logos stay editable in PowerPoint ("Convert to Shape" / "Ungroup"). Google Material Icons and SVG brand logos work directly. Recoloring an SVG logo for contrast becomes a CSS fill / color change instead of a separate raster pipeline.

Automatic font embedding

The library detects fonts used in the page and embeds them into the PPTX (via opentype.js + fonteditor-core). Decks render identically on any machine. Google Fonts works via crossorigin="anonymous" on the link tag.

Preview = export

The HTML we render in the preview is the source of truth for the export. No more "looks fine in preview, breaks in PPTX". One renderer.

Less code to maintain

lib/schema/slide.ts, components/slides/SlideRenderer.tsx, lib/bidi.ts, most of inngest/functions/deck-export.ts, the bbox/coord/bullet sections of the system prompt — all deleted.

What stays the same

  • Create wizard (content → brand → summary).
  • Inngest generation pipeline (queue, polling, status, retry).
  • Claude API integration (Opus 4.7, streaming, adaptive thinking, prompt caching).
  • DB schema for Project / Presentation / PresentationVersion (the slideJson column just stores a different shape).
  • Auth, Supabase, dashboard, settings — none of this changes.

What we know / don't know about the library

  • It still uses PptxGenJS under the hood. It's a layout-engine wrapper, not a replacement. We're not "scrapping PptxGenJS" — we're replacing our hand-coded coordinate math with theirs.
  • It is browser-only. Needs a real DOM with layout. Two integration paths: (A) client-side export from the preview window, (B) Puppeteer + dom-to-pptx server-side. We'll start with (A) for the spike; revisit (B) if we need background export jobs.
  • BiDi is unverified. The README / SUPPORTED.md / USAGE.md and the source code do not mention direction: rtl or dir="rtl" for normal text flow — only writing-mode: vertical-rl for East Asian. Whether mixed-script Arabic text round-trips correctly through the library into PowerPoint is the central open question. The spike must answer this first.
  • It's young. v1.0.0 was eight months ago; we're on 1.1.8. Single maintainer, very active (last push three days before this entry), frequent fixes in the changelog. Healthy risk profile but not a "boring tech" choice.

The pipeline (browser → PPT)

1. Claude emits {slideId, role, html} per slide
2. Preview: SlideRenderer + DOMPurify + theme CSS vars (graceful fallback when DOMPurify's SSR singleton lacks .sanitize)
3. Export click: html-export.ts
   ├─ Mount slides offscreen at 1920×1080, full opacity, no scale transform

   │   • splitMixedScriptFlexChildren — wrap direct text nodes when sibling has explicit dir or parent is flex/grid
   │   • stripArabicLetterSpacing — kill inherited letter-spacing on Arabic-bearing elements
   │   • insertScriptTransitionSpaces — insert space at any Arabic↔Latin / Arabic↔digit adjacency inside text nodes

dom-to-pptx patches (patches/dom-to-pptx+1.1.8.patch, auto-applied via postinstall)

1. Direction-blind text-align mapping (two sites)

Upstream hard-coded text-align: start → algn="l" regardless of direction. Every Arabic headline / body relying on inherited RTL came out left-aligned in PPT. Patch reads style.direction and routes start / end / unset to the correct value (algn="r" for RTL, algn="l" for LTR).

2. isTextContainer script-uniformity check

A row with mixed-script sibling element children (<span>01</span><span>Arabic</span><em>Latin</em>) used to collapse into one text frame — all pieces concatenated, visual separation lost. Patch adds taqreer_hasUniformScript(children): returns false if children have different scripts, which makes isTextContainer return false, which makes the walker recurse and emit one PowerPoint shape per child at its own bounding rect.

3. isSafeInline — bordered / rounded elements are styled boxes

Upstream check only excluded EMPTY bordered/backgrounded elements (decorative dots). Bordered text pills slipped through as "inline emphasis", got merged into the parent text frame, and rendered as plain text with no border in PPT. Patch: any element with a border OR (background + border-radius) returns false — pills, badges, chips, cards stay as their own shapes with their styling intact.

4. CSS padding as margin (two sites)

The deepest bug. Upstream read CSS padding via getPadding(), stored it as inset:, then passed it to PptxGenJS while ALSO hardcoding margin: 0. PptxGenJS uses margin (in pt) for body insets — not inset. Every text shape's CSS padding was silently discarded; <a:bodyPr> always emitted with lIns="0" rIns="0" tIns="0" bIns="0". Two text-emission code paths needed the same fix (bg-image branch + bgColor/border/textPayload branch): convert textPayload.inset (inches array) to pt and pass as margin: _paddingPt. Cards' internal padding, badges' breathing room, headlines' line-height insets — all of it finally reaches PPT.

OOXML post-processor (lib/export/bidi-postprocess.ts)

Runs once per slide XML inside the final .pptx blob:

  • PASS 1 — walk every <a:txBody>; if any descendant paragraph has strong-RTL text, flip <a:bodyPr rtlCol="1">. PptxGenJS's rtlCol="0" default overrides paragraph-level pPr rtl="1" on PowerPoint, so this had to flip first.
  • PASS 2 — for each paragraph:
    • Arabic content → pPr rtl="1", fill algn="r" only when missing (don't fight explicit author choices)
    • Smart-merge runs with identical rPr signature (script-split runs collapse cleanly; inline-coloured spans stay separate)
    • Retag run lang and endParaRPr lang to "ar-SA" so PowerPoint uses the Arabic BiDi resolver per run
    • LTR-content paragraphs inside an RTL txBody get explicit rtl="0" + default algn="r" (English titles in Arabic decks stay right-aligned but read LTR)
  • PASS 3 — direction-aware shape extension. For short (≤80 chars) text shapes UNDER 3 M EMU wide (≈33% slide width — excludes headlines), grow cx by 10% on the side OPPOSITE the text anchor; clamp to slide bounds. Absorbs PowerPoint's slightly-wider glyph metrics so single-line text doesn't wrap to two. Anchored side never moves → margins preserved.
  • PASS 4 — gradient-text sentinel swap. For every <a:rPr> whose <a:srgbClr val="FExxxx"/> matches a sentinel allocated by extractGradientIntents, drop the <a:solidFill> and insert a real <a:gradFill> built from the stashed recipe — linear gets <a:lin ang="..." scaled="1"/>; radial gets <a:path path="circle"><a:fillToRect l=t=r=b=50000/></a:path>. Bridges CSS background-clip: text + gradient → vector-sharp PowerPoint gradient on the text run, no SVG wrapper needed. Implemented in lib/export/gradient-text.ts (parser + sentinel allocator) and PASS 4 in bidi-postprocess.ts (OOXML mutation). Caveat: PowerPoint bounds run-level gradFill to the parent shape's box, so two inline gradient spans inside the same flex/grid container will read as one continuous gradient across the shape — author each gradient text element as its own block-level element to get independent per-element gradients.

C. DOM preprocess + gradient extractor — lib/export/html-export.ts + lib/export/gradient-text.ts

  1. splitMixedScriptFlexChildren (html-export.ts). Wrap direct text nodes in a <span> when the parent is a flex/grid container with mixed-script siblings, OR when an element child has explicit dir. Lets the patched isTextContainer see non-uniform script element children and recurse → one shape per child at its measured position.
  2. stripArabicLetterSpacing (html-export.ts). Kill inherited letter-spacing on any element directly bearing Arabic text. CSS letter-spacing breaks Arabic contextual shaping (the connecting glyphs decouple).
  3. insertScriptTransitionSpaces (html-export.ts). Insert a space at every Arabic↔Latin / Arabic↔digit adjacency inside text nodes so PowerPoint's BiDi resolver doesn't glue them into the wrong script run.
  4. extractGradientIntents + sentinel-hex bridge (gradient-text.ts). Multi-stop, explicit percentages, multi-layer backgrounds, radial — all covered; conic + repeating-* skip cleanly. parseColorToHex front-gates on CSS.supports('color', input) so non-color keywords like circle can't slip through canvas fillStyle's "keep previous on invalid" behaviour. Per-element sentinels (no recipe dedup) keep separate gradient elements as separate runs so PASS 2's run-merge doesn't collapse them.

  1. Caveats and known limits worth tracking

  • Run-level gradFill bounds to the parent shape, not the run. Two inline gradient spans inside the same flex/grid container will read as one continuous gradient stretched across the shape — this is an OOXML semantic limit, not a bug we can fix in the post-processor. Author each gradient text element as its own block-level node to get independent per-element fills.
  • Run-merge collapses per-run formatting in RTL paragraphs. PASS 2's smart-merge keeps the first run's rPr when collapsing script-split runs. Acceptable today (uniform-style paragraphs); needs a "merge by compatible rPr" pass when inline-styled spans inside one paragraph become a real use case.
  • Alpha in gradient stops is dropped. Our parseColorToHex ignores alpha channels — colour-to-alpha gradients (e.g. radial-gradient(rgba(0,0,0,0), rgba(0,0,0,0.5))) round-trip as opaque. Keep the prompt rule that pushes those to inline SVG with stop-opacity.
  • Conic and repeating gradients are skipped, not rendered. The extractor returns null for them; dom-to-pptx falls back to whatever it does for unrecognised CSS (usually a flat colour). Prompt rule already forbids them.
