AI Presentation Platform

Taqreer Full-Stack Web App Architecture

A complete product and technical plan for Taqreer (taqreer.ai): an Arabic-first, RTL AI presentation platform where users provide content, Claude designs the deck, and users review, comment, regenerate, or export. There is no manual slide editor — Claude does all the design work.

Product Type AI presentation generator (Arabic-first, RTL)
Stack Next.js 16, TypeScript, Tailwind, Prisma/Postgres, Inngest, Supabase, Anthropic Claude API
Core Output PPTX, PDF, saved projects, reusable templates
Main Differentiator Promptless brand-aware generation; no manual editing — every change goes through Claude

01. Product Overview

Taqreer turns content into beautiful Arabic presentations. The user provides content, brand assets, an existing deck to improve, a reference deck to mimic, or a template to start from. Claude generates the slide design as structured JSON. The user lands in the Preview Window to review, comment on specific areas (Claude redesigns them), regenerate the whole deck, export to PPTX/PDF, or save as a template.

Flow 1 — Create (إنشاء)

Start from scratch. User pastes/uploads content, sets brand (palette, fonts, logo), and Claude designs a fresh deck.

Flow 2 — Enhance (تحسين)

Upload an ugly PPT. Claude extracts its existing theme/palette/fonts and redesigns the layout while preserving the original visual identity.

Flow 3 — Mimic (محاكاة)

Upload your content + a reference deck whose style you admire. Claude extracts the reference's style contract and rebuilds your content in that style. Iterative review loop.

Flow 4 — From Template (إنشاء من قالب)

Pick a template from the library, add content, and Claude maps the content into the template's design system. No brand wizard — the template supplies the design tokens.

Core product rule: every journey ends inside the Preview Window. The preview is review-only — users browse slides, comment on areas (which fires area.redesign.requested to Claude), regenerate the whole deck, export to PPTX or PDF, or save as a template. There is no manual slide editor — Claude does all the design work.

02. Product Flows

Four primary flows on the dashboard, RTL right→left: Create, Enhance, Mimic, From Template.

Flow 1: Create (إنشاء) — start from scratch

Dashboard tile 1 → /create/content. Three-step wizard, brand decided fresh by Claude.

1
Content (/create/content)Upload PPTX/PDF/DOCX/TXT/images or paste text.
2
Brand & Settings (/create/brand)Upload a palette screenshot for Claude vision or pick colors manually; upload heading + body fonts and logo; pick slide size and count.
3
Editable AI Summary (/create/summary)Claude returns extracted palette, font samples, logo, and a content outline — all editable. CTAs: إنشاء or إنشاء وحفظ كهوية بصرية.
4
Generate (/create/generating)Fires Inngest deck.generate.requested. Slides stream in via Supabase Realtime, then auto-redirect to /preview/[projectId].

Flow 2: Enhance (تحسين) — preserve original theme/colors

Dashboard tile 2 → /enhance. Goal: make an ugly PPT better while keeping its original visual identity. Claude redesigns layout/typography/hierarchy but does not invent a new theme.

1
Upload (/enhance)PPTX-only upload. Advanced options: keep colors, keep fonts, custom instructions.
2
Review (/enhance/review)Claude extracts and shows the original palette, fonts, logo, and slide structure, plus a plain-Arabic redesign plan. The user can override any extracted asset before confirming.
3
GenerateFires deck.generate.requested with type: "enhance" and the extracted (possibly overridden) brand contract. Lands on shared preview.

Flow 3: Mimic (محاكاة) — redesign in a reference style

Dashboard tile 3 → /mimic. Take your content and rebuild it in the style of a reference deck you admire. Two uploads, iterative review.

1
Your content (/mimic/content)Upload PPTX/PDF/DOCX/TXT or paste the content to redesign.
2
Reference style (/mimic/reference)Upload a PPTX whose visual style you want to match. Claude extracts the reference style contract: palette, fonts, layout idioms, accents.
3
Review — iterative (/mimic/review)Claude shows the extracted reference style and a slide-by-slide design plan. User confirms, or adds a prompt → Claude refines → updated review → loop until confirmed.
4
GenerateFires deck.generate.requested with type: "mimic" plus content + reference style contract. Lands on shared preview.

Flow 4: From Template (إنشاء من قالب) — pick template, add content

Dashboard tile 4 → /templates. Replaces the earlier "Create Template From Scratch" concept entirely — there is no separate custom-design flow; the design comes from a pre-existing template, and the user just contributes content.

1
Browse library (/templates)Grid of templates with search and filters (category, industry, language, direction, plan). Each card has a إنشاء من هذا القالب CTA.
2
Add content (/templates/[id]/content)Upload PPTX/PDF/DOCX/TXT or paste. Slide-count options. No brand wizard — the template supplies the design system.
3
GenerateFires deck.generate.requested with type: "custom" and the template's style_contract applied as the design system. Lands on shared preview.

08. AI Pipeline

The AI system should be split into multiple controlled stages instead of one large prompt. Each stage should return structured data and pass validation before moving to the next stage.

Create Deck From Content

1
Parse contentExtract clean text, headings, lists, tables, images, and source structure.
2
Analyze brandExtract colors, typography, logo rules, image style, tone, and layout patterns.
3
Generate outlineCreate presentation title, sections, slide list, and slide objectives.
4
Create slide narrativeDefine the role of each slide and the message it should communicate.
5
Select layoutsMap each slide to a suitable slide type.
6
Generate slide JSONCreate structured slide elements, positions, styles, and assets.
7
Validate outputCheck schema, overflow, missing assets, coordinates, and RTL rules.
8
Open Preview WindowDeck opens at /preview/[projectId] for review, area comments, regen, and export.

Enhance Existing Deck

1. Upload original PPTX
2. Parse slides into internal JSON
3. Extract current palette, fonts, logo, slide structure (Claude vision)
4. Show extraction + redesign plan on /enhance/review for user confirmation/override
5. Generate improved slide JSON, preserving original brand
6. Zod validate; self-healing retry on failure
7. Save to PresentationVersion
8. Open Preview Window

Mimic Reference PPT

1. Upload your content (/mimic/content)
2. Upload reference PPTX (/mimic/reference)
3. Extract content from your upload
4. Extract style contract (palette, fonts, layout idioms) from reference (Claude vision)
5. Show /mimic/review with plan in Arabic; user confirms OR re-prompts (iterative loop)
6. Generate slide JSON: your content × reference style
7. Zod validate; self-healing retry on failure
8. Save to PresentationVersion; open Preview Window

09. Preview Window

The Preview Window is review-only — there is no manual slide editor. Users do not drag, resize, or type on a slide. Claude does all the design work; the user's interaction after generation is to review, comment, regenerate, export, or save as a template.

Layout

┌────────────────────────────────────────────────────────────┐
│  Action bar:  أعد التصميم  ·  تصدير PPTX  ·  تصدير PDF  ·  حفظ كقالب  │
├──────────────────────────────────┬─────────────────────────┤
│                                  │  Slide 1                │
│      Main slide view             │  Slide 2                │
│      (1920×1080 rendered as      │  Slide 3  ← selected    │
│       HTML/CSS, scaled to fit)   │  ...                    │
│                                  │  Slide N                │
└──────────────────────────────────┴─────────────────────────┘

What the user can do

  • Browse slides via the right-side slide panel
  • Click-and-drag to select an area on the main slide → opens a comment box → submits to area.redesign.requested Inngest job → Claude updates JSON for those elements → slide re-renders
  • Trigger a full regeneration with the same brief (action bar أعد التصميم)
  • Export as PPTX (PptxGenJS, via deck.export.requested)
  • Export as PDF (Puppeteer, via deck.export.requested)
  • Save the deck as a template (style contract + thumbnails + PPTX artifact, via template.save.requested)

What the user cannot do

Move elements. Resize elements. Change font/color manually. Add a text box. Reorder slides by hand. Undo to a previous "manual edit." None of these exist. Every visual change goes through Claude via a comment or a regen — that's the deliberate product constraint that keeps the JSON-first architecture coherent.

Rendering approach

Slides render as HTML/React using absolute-positioned elements on a fixed 1920 × 1080 canvas. The same coordinate system is used for the preview itself, slide-panel thumbnails (via html2canvas when saving as a template), PPTX export (PptxGenJS), and PDF export (Puppeteer printing the HTML). The renderer component lives at components/slides/SlideRenderer.tsx.

Current implementation status

As of 2026-05-11, /preview/[projectId] exists with a minimal first cut: it loads the latest completed PresentationVersion from Prisma, links Google Fonts CSS from the manifest, and stacks all slides vertically at 50% scale. The action bar, slide-panel side navigation, area-select-and-comment overlay, and per-element shadow/border rendering are not yet built — see §15 Implementation Status.

12. Export System

The export service converts internal presentation JSON into external formats. Export jobs should run in the background.

PPTX Export

1
Read presentation JSONUse the saved deck as the source of truth.
2
Convert slide dimensionsMap 1920 × 1080 coordinates to 16:9 PowerPoint size.
3
Render elementsConvert text, images, shapes, charts, and tables into PPTX objects.
4
Generate PPTXCreate the file and store it in object storage.
5
Return download URLSave the export record and show it to the user.

PDF Export Options

Option A: HTML to PDF

Render slides in the browser using the same React slide renderer, then export to PDF with Playwright or Puppeteer. Best for MVP fidelity.

Option B: PPTX to PDF

Generate PPTX first, then convert to PDF using a worker with LibreOffice. Better for PowerPoint consistency, but more infrastructure-heavy.

MVP recommendation: start with PPTX export and HTML-to-PDF export. Add LibreOffice conversion later if needed.

14. Development Phases

Build the app in controlled phases. Do not start with all features at once.

Phase 1: Foundation

  • Set up Next.js, TypeScript, Tailwind, shadcn/ui.
  • Set up authentication.
  • Set up PostgreSQL and ORM.
  • Set up object storage.
  • Connect landing page and dashboard.
  • Create project creation flow.

Phase 2: Presentation JSON Engine

  • Define presentation, slide, and element schemas.
  • Build slide renderer.
  • Build slide thumbnail renderer.
  • Save and load presentation JSON.
  • Validate slide JSON with Zod.

Phase 3: AI Deck Generation

  • Parse pasted content.
  • Upload logo and brand files.
  • Generate brand kit JSON.
  • Generate presentation outline.
  • Generate slide JSON.
  • Show progress UI.

Phase 4: Preview Window MVP

  • Build the slide-panel side navigation (thumbnails).
  • Build the main slide view (full SlideRenderer at scale).
  • Build the action bar: أعد التصميم, تصدير PPTX, تصدير PDF, حفظ كقالب.
  • Wire the area-selection overlay → comment box → area.redesign.requested.
  • Subscribe to Supabase Realtime so re-rendered slides stream in after an area redesign.

Phase 5: Export

  • Generate PPTX from internal JSON.
  • Generate PDF from slide renderer.
  • Store exported files.
  • Create export history.

Phase 6: Templates Library + Flow 4 (From Template)

  • Templates library page (/templates) with search, category/industry/language/direction/plan filters, and featured section.
  • Per-template detail / preview with إنشاء من هذا القالب CTA.
  • Apply template style contract to user content via /templates/[id]/content → deck.generate.requested with type: "custom".
  • Save current project as template (writes JSON style contract, captures thumbnails via html2canvas, generates PPTX artifact).
  • Support user-saved + community templates with use_count tracking.

Phase 7: Enhance Flow (تحسين)

Make an ugly PPT better while keeping its original theme/colors. Enhance is a standalone flow — not a parent of Mimic.

  • Upload PPTX (/enhance) — already shipped.
  • Parse PPTX and run Claude vision/extraction: palette, fonts, logo, slide structure.
  • Review page (/enhance/review) — display extracted assets + Claude's redesign plan in Arabic; allow per-asset overrides before generation.
  • Fire deck.generate.requested with type: "enhance" and the (possibly overridden) extracted brand contract.

Phase 8: Mimic Flow (محاكاة)

Take user content and redesign it in the visual style of a reference deck. Two uploads + iterative review.

  • Content upload (/mimic/content) — PPTX/PDF/DOCX/TXT/paste.
  • Reference style upload (/mimic/reference) — Claude extracts reference style contract (palette, fonts, layout idioms, accents).
  • Review (/mimic/review) — iterative loop: Claude shows reference style + slide-by-slide design plan; user confirms OR adds prompt → Claude refines → updated review.
  • Fire deck.generate.requested with type: "mimic" and content + reference style contract.

Snapshot of what's actually working in the repo as of this date, plus traps we hit and the rules that came out of them. Update on each meaningful shipping milestone.

Lessons learned — do not repeat

PowerShell shadows ANTHROPIC_API_KEY

The PowerShell harness used in this project exports ANTHROPIC_API_KEY="" as an empty string. Next.js gives shell-env precedence over .env.local, so process.env.ANTHROPIC_API_KEY ends up empty despite a valid key in the file.

Fix: always Remove-Item env:ANTHROPIC_API_KEY -ErrorAction SilentlyContinue before npm run dev. Confirm with: Get-ChildItem env:ANTHROPIC* — if the var is listed with a blank value, this is the issue.

Anthropic SDK client must be lazy

new Anthropic() at module load captures whatever process.env.ANTHROPIC_API_KEY is at import time. If env loading races module load, the client captures empty permanently.

Fix: wrap construction in a getClient() function called inside step.run() at request time, and throw a clean error if the key is still missing.

Slide schema too complex for structured outputs

Passing zodOutputFormat(SlideManifestSchema) to output_config.format returns 400 "The compiled grammar is too large". The schema's discriminated unions × deep nesting × many enums blow the strict-grammar limit.

Fix: drop output_config.format; use a strong system-prompt that describes the JSON shape, parse the response text with markdown-fence stripping, validate with Zod, and retry with the validation error appended to the prompt (3 attempts inside the Inngest step). This is the "self-healing" pattern from the brief.

Strip previewDataUrl from Claude input

The Create wizard sent the logo as a base64 data URL (previewDataUrl) in addition to the storage URL. That bloated each Claude call by ~3000 input tokens for no benefit — the renderer can use storageUrl alone.

Fix: drop previewDataUrl when building the Claude-bound brief in app/api/projects/route.ts (already applied 2026-05-11).

Prisma table names are PascalCase

When querying directly from psql, table names must be double-quoted PascalCase: "PresentationVersion", "Presentation", "Project", etc. — not snake_case. Same for column names: "slideJson", "presentationId", "createdAt".

Inngest function updates v1 (don't create v2)

POST /api/projects creates a v1 PresentationVersion with status queued. The original deck-generate handler created a new v2 with status completed, leaving v1 stuck at queued forever. The rewrite updates the v1 row using versionId from the event payload. (The new /regenerate route is the correct place to create v_n+1 and fire generation against it.)

PPTX coordinates: px × (SLIDE_W_IN / CANVAS_W) × 72

The CSS-px→pt ratio at 96 DPI is 0.75, but our 1920px canvas is scaled to a 10″ slide — the right factor for font size and positioning is (10/1920) × 72 = 0.375. Using 0.75 doubled every glyph and made stat numbers wrap inside their cards. Also: pick LAYOUT_16x9 (10×5.625″) so the inch-constants match what PptxGenJS expects.

Pick the slide font by script, not role

The earlier rule ("headlines use heading font, body uses body font") tagged Arabic caption/label elements with Poppins (the body font). On any machine without Cairo installed, PowerPoint fell back to a Latin font and the Arabic letters visibly disconnected. The new rule: pick by script. Arabic content → Cairo, Latin → Poppins. Role drives weight/size only.

Send-after-commit is not atomic

Routes that fire Inngest events after a Prisma transaction (/api/projects, /retry, /regenerate, /export, /save-as-template) can leak orphaned "queued" rows if the send fails. Always wrap with sendInngestEventWithRetry (in lib/inngest-helpers.ts) and on final failure revert Project/Version/Job statuses to failed so the UI surfaces a clear error instead of an infinite spinner.

Ban gradients in slide JSON

PptxGenJS doesn't expose multi-stop linear gradients on slide backgrounds or shape fills. The closest workaround is a solid color + half-transparent overlay rectangle, which is a mediocre approximation. The system prompt now forbids {type: "gradient", ...} in slide.background and shape.fill entirely. For two-color effects, Claude paints a full-canvas rect in one color and overlays a second shape at lower opacity — clean to export. Schema still accepts gradients (so old decks render); the generator just doesn't emit them.

Coding Rules (from globals.css)

The top comment of app/globals.css is the canonical reference for the design system. The rules below are not optional — CodeRabbit will flag violations.

Token-driven, not hex-driven

Build new UI by composing semantic classes — never hardcode hex values or rgba() in TSX. Token layers (bottom→top): brand palette (--tq-blue, --tq-magenta, --tq-violet, --tq-lavender), surfaces (--tq-surface-*, --tq-bg), text (--tq-text-*), borders (--tq-border-*), gradients (--tq-gradient-*), shadows (--tq-shadow-*), radii (--tq-radius-*), glass system (--glass-*).

Class catalog (must use, not redefine)

Cards: .glass-card, .glass-empty-state, .glass-card-danger. Overlays: .glass-dropdown, .glass-modal. Buttons: .btn-gradient (primary), .btn-outline-dark (secondary), .btn-danger. Nav: .nav-item, .nav-active, .dropdown-item. Text: text-white (Tailwind utility), .text-muted. Forms: .input-dark, .input-search, .status-success, .status-error. Avatars: .tq-avatar-ring, .tq-avatar-fallback. Misc: .tq-thumbnail, .tq-card-divider, .badge-purple, .plan-banner, .progress-track/.progress-bar, .divider-dark, .page-container.

Glass system is runtime-tunable

The glass card opacity/blur/saturation are CSS variables (--glass-opacity, --glass-blur, --glass-border-opacity, --glass-saturation) initialized by an inline <script> in app/layout.tsx before paint, and switchable live from Settings → مظهر التطبيق. .glass-dropdown and .glass-modal are intentionally not preset-responsive.

Page chrome

All authenticated app pages must use the page-container class on the root element. Always use Tailwind utility classes; reach for globals.css semantic classes only when Tailwind can't express it. Raw CSS in inline styles is a smell — flag it.

Code review — CodeRabbit

We use CodeRabbit for AI-driven code review of the dev branch before merging into main. Reviews catch the kinds of issues a human reviewer would catch: race conditions, missing defensive checks, leaks, design-system drift, HTML correctness, etc.

Installation (Windows + WSL)

Native Windows is unsupported by the installer. Install in WSL Ubuntu:

curl -fsSL https://cli.coderabbit.ai/install.sh | sh

Plus the Claude Code plugin:

Authentication (one-time)

Must be run from a real interactive terminal, not from inside Claude Code:

Opens a browser to complete OAuth. Token persists in WSL after that.

Running a review

From D:\taqreer in PowerShell (the WSL command inherits the cwd as /mnt/d/taqreer):

# Compare current branch (dev) against origin/main — what would be in a PR
wsl coderabbit review --base origin/main

# Only uncommitted changes
wsl coderabbit review --type uncommitted

# Structured JSON output for agent workflows
wsl coderabbit review --base origin/main --agent

Reviews are cached server-side per diff hash; re-running the same diff returns "no findings" because the prior findings are considered shown.

When to run it

Before merging dev → main. Also useful after any batch of meaningful changes (a feature branch, a refactor pass). The 2026-05-11 review on dev vs origin/main surfaced 20 findings — most actionable, a few cosmetic. Fix the reliability and bounds issues first; style-guideline violations (missing page-container, inline styles) can be a separate refactor pass but should not pile up.

Cost data point (2026-05-11): First end-to-end generation (5 Arabic slides, Opus 4.7 + adaptive thinking, no prompt cache yet): ~7600 input tokens, ~6400 output tokens, ~75s wall-clock. After the cache warms, subsequent runs should see ~90% of the system prompt as cache reads.

16. Technical Risks and Recommendations

These are the main areas that can slow development or affect output quality.

PPTX import is complex

Do not promise perfect PPTX-to-slide-JSON conversion at MVP stage. The Enhance flow's PPTX parsing should extract palette, fonts, logo, content outline, and rough slide structure — Claude redesigns from there. Don't aim for pixel-perfect round-tripping.

AI layout quality can vary

Use strict slide types, layout templates, schema validation, overflow checks, and design scoring.

Export fidelity can break

Use the same 1920 × 1080 coordinate system across the Preview Window, thumbnails, PDF, and PPTX export.

RTL cannot be added later

Arabic direction, right alignment, font fallback, and RTL layout rules must be part of the initial schema.

Critical recommendation: avoid letting Claude's output land in PresentationVersion.slideJson without validation. Every Claude response goes through Zod validation; on failure, retry with the validation error appended to the prompt (self-healing pattern). After 3 failed attempts the Inngest job fails and surfaces in Sentry.
